Learn lw by doing

You start with sources — an article, a paper, a saved chat — and end with a small, cross-linked markdown wiki where every claim cites where it came from. lw is the compiler in the middle. An agent proposes the pages, and you decide what lands.

How to use this page Each lesson has a goal, the commands, what you should see, and a short check at the end. Open a terminal next to it and type along. Mark a lesson done when you've run it. Your progress is saved in this browser only. The terminal output shown here comes from real runs. Long output is trimmed, and trims are marked with ….

00The mental model

Goal: know the two rules that explain every design choice in lw, before you type anything.

1 · The agent gets no filesystem

Its tool list has no write, edit, delete or bash. They aren't blocked. They're simply not offered. The only way the agent can change anything is through stage.* tools, which check each change and add it to a buffer.

2 · Nothing lands without your review

Every proposal goes into a changeset that you review hunk by hunk. Rejections are journalled too, so the history shows what the agent tried, not just what got in.

Everything else follows from these two rules. One loop runs again and again:

TermMeaning
VaultA directory with a SCHEMA.md. lw walks up from your current directory to find the nearest one, or you pass --vault <dir>.
raw/Ingested sources. Written once, never changed. Every claim cites back into here.
wiki/Reviewed pages: entities/, concepts/, comparisons/, queries/.
ChangesetOne reviewable unit of proposed ops (create_page, patch, rename, …). Only one can be open at a time.
SessionThe recorded agent conversation that produced a changeset. They share one id.
JournalThe append-only event log (.llmwiki/journal.ndjson) that lw log reads.
Check: the agent wants to fix a typo in a page. How does it do that?

It calls a stage.* tool (for example stage.patch_page). That adds a proposed op to the open changeset. The page on disk doesn't change until you review and commit.

01Install & connect a provider

Goal: a working lw binary that can reach a model with tool calling.

Install

# from source
git clone https://github.com/awepo-pro/lw && cd lw
make build                     # → ./lw

# or with Go 1.25.8+
go install github.com/awepo-pro/lw/cmd/lw@latest

# or Homebrew / Nix
brew install awepo-pro/tap/lw
nix profile install github:awepo-pro/lw
$ lw version
lw v2.63.0

The version comes from the release tag the binary was built from, so a bug report can name the exact build.

Point it at a model

lw sends requests in the plain OpenAI chat-completions format and defaults to DeepSeek. lw config shows what lw will actually use:

$ lw config
llm.base_url               = https://api.deepseek.com/v1   (default)
llm.model                  = deepseek-v4-flash   (default)
llm.api_key                = env:DEEPSEEK_API_KEY (missing)   (default)
llm.temperature            = 0.2   (default)
llm.max_tokens             = 32768   (default)
llm.limits.max_tool_rounds = 24   (default)
llm.limits.context_tokens  = 96000   (default)
…
The key is a reference, not a value. The config file stores env:DEEPSEEK_API_KEY (or keyring:NAME), and lw reads the variable only when it needs it. If you paste a literal key, lw rejects it with a warning. The key never shows up in output, in the config file, or in the vault. 
export DEEPSEEK_API_KEY=sk-...

# another OpenAI-compatible provider? set both together:
lw config set llm.base_url https://api.deepseek.com/v1
lw config set llm.model    deepseek-v4-flash
lw config set llm.api_key  env:MY_PROVIDER_KEY   # if your variable has another name

# end-to-end check: resolves the key, calls the model, confirms tool calling
lw config --probe
The #1 setup mistake llm.base_url must be an OpenAI-compatible /v1 endpoint. https://api.deepseek.com/anthropic looks fine, but every request to it returns a 404. Also, do not end the URL in /chat/completions: lw adds that path itself and rejects any base URL that includes it.

A healthy setup, as shown by lw doctor:

✓ config   api_key env:DEEPSEEK_API_KEY (set) · model deepseek-v4-flash @ https://api.deepseek.com/v1
✓ provider deepseek-v4-flash reachable, tool calling ok (1568ms)
Try it
Unset the key (unset DEEPSEEK_API_KEY) and run lw config --probe. It fails right away and tells you what to fix, without making a network call. Export the key again before you continue.

02Create a vault

Goal: an empty but valid vault, and a picture of what each file is for.

$ mkdir ml-wiki && cd ml-wiki
$ lw init --schema ml-systems
initialized vault in /home/you/ml-wiki
  domain           ml-systems
  tags             10 (10-20 recommended)
  files            SCHEMA.md, index.md, log.md, curator-memory.md, .gitignore
  directories      raw/{articles,papers,transcripts,assets}, wiki/{entities,concepts,comparisons,queries} (8 of 8 created)
  engine           .llmwiki/ (staging engine state)
next: lw config — point lw at a provider, then lw ingest <url> to add the first source

If you leave out --schema, init asks you for the domain, the tag list, and page-type conventions.

PathWhat it is
SCHEMA.mdThe domain and its 10–20 tags. Every page's tags: must come from this list.
index.mdCatalog of every page, one line each, organized in sections. The engine keeps it in sync.
log.mdAppend-only log for humans. Rotates at 500 entries.
curator-memory.mdThe agent's standing editorial preferences. It's a normal page, so you can edit it.
raw/…Ingested sources, written once and never changed.
wiki/…Reviewed pages, one directory per page type.
.llmwiki/Engine state: object store, changesets, journal, search index, transcripts. Listed in .gitignore. Deleting it loses history, not your notes.
$ lw status
0 pages · 0 raw · 10 tags
lint: 0 errors, 0 warnings, 0 info
no open changeset
$ lw lint
clean
Check: you're in ml-wiki/wiki/concepts/. Does lw status work?

Yes. lw walks up to the nearest ancestor that contains SCHEMA.md. Only init doesn't need to be inside a vault.

03Ingest your first source

Goal: turn one article into proposed pages, and understand what was proposed vs. what was written.

lw ingest ~/Downloads/kv-cache-explained.md   # a local file
lw ingest https://example.com/some-post        # or a URL
lw ingest ~/notes/                             # or a folder (.md .txt .html .pdf)

lw first converts each source to fixed markdown. If a path or URL is bad, the whole command fails before any changeset is opened. Every new ingest also saves a verbatim original file beside the raw markdown (e.g. .md.orig, .html, .txt, .pdf), and local markdown images are copied into raw/assets/ and linked as ../../raw/assets/<name>.

Then the agent reads the source, SCHEMA.md, index.md, and recent log.md, and proposes pages. Ingest turns compile only the sources you gave them: web.search is not offered. To keep the agent writing instead of wandering, an ingest may read at most 6 existing wiki pages between two staged changes, and may make at most 10 wiki.search calls before staging a page (an 11th search is refused). It also can't repeat a read whose answer is still in its context, so it doesn't spend rounds looking at the same page twice. If a network or provider error interrupts the turn, lw retries with backoff and keeps whatever ops were already staged, marked [partial: …]. A real run that took about three minutes ends like this:

opened changeset cs-92c7d850b461792a: ingest ~/Downloads/kv-cache-explained.md (4 op(s))
  op1 ingest_source raw/articles/kv-cache-explained.md
  op2 create_page wiki/concepts/kv-cache.md
  op3 create_page wiki/concepts/autoregressive-decoding.md
  op4 create_page wiki/queries/reducing-kv-cache-memory.md
Nothing has been written yet. op1 is always the immutable copy of your source. It records the original source_url and a sha256 of the body, which lw later uses to detect drift. Every create_page after it can only cite that source, because it's the only thing the agent has read.

If a changeset is already open (say, from an Ask turn), the ingest adds to it instead of opening a second one, and the first line says so: joined changeset cs-… rather than opened changeset cs-….

Two small repairs happen as pages are staged, and the agent is told about each one. If a section edit repeats the section's own heading (## Trade-offs inside the Trade-offs section), the duplicate heading is removed. If a page's body cites a raw/ source that its sources: frontmatter doesn't list, the source is added. Both used to show up as lint warnings after an ingest.

Recompiling and attaching originals

If you want to re-run compilation on a raw source you already committed (perhaps with a new schema or after updating curator memory), use --recompile. It reads from the committed raw source and stages new or updated wiki pages without staging a duplicate raw file:

lw ingest --recompile raw/articles/kv-cache-explained.md

For sources ingested before lw saved originals, backfill the verbatim original without calling a model or staging pages:

lw ingest --attach ~/Downloads/kv-cache-explained.md

Re-ingesting an edited source

Edit an article you already ingested and ingest the same path or URL again. lw saves the new text as a new raw (paged-attention-2.md), never over the old one, and records the link in its frontmatter:

$ head -6 raw/articles/paged-attention-2.md
---
source_url: /home/you/Downloads/paged.md
ingested: 2026-11-01
sha256: 64b72f9a456b9e39e843de36a118e3a311298abf849bcd14e59464b52d30ffe2
supersedes: raw/articles/paged-attention.md
original: raw/articles/paged-attention-2.md.orig

The curator is told about it: the brief (lesson 11) or the ingest_source result carries a line like this, naming the pages that cite the old raw:

- raw: raw/articles/paged-attention-2.md
  chunks: 1
  title: Paged attention
  original source: /home/you/Downloads/paged.md
  This source revises raw/articles/paged-attention.md. Pages citing the old raw: wiki/concepts/paged-attention.md. Re-read each and stage.patch_page it to cite the new raw (keep every claim; fix sources:).

If a page is left pointing at the old raw, lw lint says so (this is the cite-superseded check, a warning, not an error):

wiki/concepts/paged-attention.md:0: warn: cites raw/articles/paged-attention.md in the body, superseded by raw/articles/paged-attention-2.md; re-point it to the new raw (cite-superseded)

The old raw stays committed, so nothing is lost and old citations still resolve. Re-pointing is an ordinary reviewed patch.

Limits and dry runs

A single ingest is capped at 10 files and 75% of the context budget in bytes (282 KB at the default context_tokens = 96000). The agent still needs room to read back what it wrote. If you go over the cap, nothing is opened, and the error names the largest file so you know which one to split out. Sources the vault already holds are skipped before anything else happens.

$ lw ingest --dry-run ~/notes/
within limits: 3 files, 8 KB (limit 10 files, 282 KB)

--dry-run extracts every source and prints the result, but makes no changeset and no model call. URLs are still downloaded, because their size can't be checked otherwise.

Try it
Run lw ingest --dry-run on a folder of your own notes. Then ingest one small article for real, and run lw diff --op op1 to see the frontmatter lw added to the raw copy.

04Review the changeset

Goal: read exactly what would land, before it lands.

While a changeset is open, lw status counts only committed content. "0 pages" means nothing has landed yet, not that nothing happened:

$ lw status
0 pages · 0 raw · 10 tags
lint: 0 errors, 0 warnings, 0 info
open changeset cs-92c7d850b461792a: ingest ~/Downloads/kv-cache-explained.md (4 op(s), 0 stale; schema=pass lint=pass orphans=0 broken_links=0)
$ lw diff --stat
wiki/concepts/autoregressive-decoding.md | +30 -0
wiki/concepts/kv-cache.md | +38 -0
wiki/queries/reducing-kv-cache-memory.md | +34 -0
index.md | +5 -0
raw/articles/kv-cache-explained.md | +27 -0
5 file(s) changed, 134 insertion(s)(+), 0 deletion(s)(-)
CommandShows
lw diff --statOne line per file
lw diffFull unified diff, one hunk per changed section
lw diff --op op3Just one operation's files
lw lintLint on the projected tree, which catches problems before you commit

The TUI's Review screen (lesson 7) shows the same diff, plus two things a plain diff lacks: the agent's rationale for each change, and its provenance back into raw/.

Each hunk records the line where it starts, and it's applied the way patch applies a hunk. When you drop a hunk and restore it later, the page comes back byte for byte. A change to the frontmatter (the block between the --- lines) is never in the same hunk as a change to the body, so you can drop one and keep the other.

A stale op is one that was proposed against a file that has changed on disk since. lw won't apply it on top of your edit.

05Commit — or throw it away

Goal: land the pages, and know the two safety checks a commit runs.

$ lw commit -m "first pages from kv-cache-explained"
committed 000001
$ lw status
3 pages · 1 raw · 10 tags
lint: 0 errors, 0 warnings, 0 info
no open changeset

A commit is refused if…

  • a target file changed on disk since the op was proposed (the op is stale), or
  • it would leave lint with more errors than the last commit. --force overrides this, and the override is itself recorded in the journal.

There's no lw reject command. To throw a changeset away, discard it:

lw doctor --discard-changeset    # or press X on the TUI's Review screen

Nothing is deleted. The buffer moves to changesets/rejected/, and lw log --rejected shows it afterwards.

Lint severities Only an error makes lw lint exit non-zero. warn and info don't. A single-source page with confidence: low produces an info finding. That's normal and means "find a second source when you can", not "fix this now". There are 18 checks in total; see vault-schema.md.
Check: you hand-edited kv-cache.md while a changeset patching it was open. What happens at commit?

The op is stale and the commit is refused, so your edit is never silently overwritten.

06Ask questions

Goal: get cited answers from your own pages, and keep the good ones.

$ lw query "What is the KV cache, and why does per-token cost drop from O(n) to O(1) during decoding?"
The **KV cache** stores the key and value projections a transformer computes during decoding, so
each new token only computes attention *against* the cached keys and values instead of recomputing
them for the whole prefix. ^[raw/articles/kv-cache-explained.md] …

lw query is read-only. It never opens or leaves behind a changeset. Each claim ends with a marker that points at the raw evidence, ^[raw/…], with p.N added when the source is a paper with page anchors. If you ask about something you haven't ingested, the curator says so under Not from your vault: instead of making up a citation.

Asks are changeset-aware: an ask reads both committed pages and any pages currently staged in the open changeset, labelling staged content unreviewed. If an open changeset has been waiting for review for more than 24 hours, lw query surfaces a note reminding you to review or discard it.

Keyless ask with your own agent

If you don't have an API key configured (or hit provider rate limits), lw doesn't block you. It prints an agent fallback hint:

hint: no LLM API key is configured. An agent with its own model can still answer from this vault: lw query --prepare "<your question>"

Run lw query --prepare "<question>". It prints an ask brief with the question, vault orientation, and rules. Your external agent (or the lw-ask skill) then runs read-only tools via lw tool --ask <name> '<json>' (such as wiki.search, wiki.get, raw.get) and synthesizes the answer with its own model—calling no provider from lw and needing no API key (see lesson 12).

Keep an answer

In the TUI's Ask screen, an answer that cites the vault (it contains a ^[raw/…] or ^[wiki/…] marker) can be saved with ctrl+s. That stages a wiki/queries/ page, which you review like any other change. A read-only ask turn opens no changeset until you save or stage something. An answer with no vault citation can't be saved: "this answer cites no vault source; nothing to save".

Web lookup (optional)

Configure Tavily and the curator gets web.search for Ask turns. (Ingest turns never get web.search.) When you don't configure it, the tool isn't offered at all. A search result only becomes a source after it's ingested with stage.ingest_source, and it goes through review like everything else.

# config.toml
[web]
api_key = "env:TAVILY_API_KEY"

# shell
export TAVILY_API_KEY=tvly-...

07The TUI

Goal: do the whole ask → review → commit loop without leaving the terminal UI.

Run lw with no command (or lw tui). It needs a terminal of at least 80×24. tab cycles through five screens:

Review → Ask → Lint → Log → Browse   (wrapping back to Review)

The header shows the vault counts and the open changeset, including how long it has been waiting for review (e.g. cs-1c86cb (15m) · 1 op · checks ✓). The footer always lists what the current screen's keys do. Press ? for every key.

Ask, then Review

Type a request and press enter. An ask runs read-only and opens no changeset until it actually stages something. It can read back staged-only pages via wiki.get, labelling staged content unreviewed. While you're on Ask, q and ? type into the message box, so quit with ctrl+c.

╭ Transcript — cs-fd447f ─────────────────────────────────────────── ↑ 28 earlier ╮
│ ▸ stage.close {}  → changeset cs-fd447f752de3e221                               │
│ assistant                                                                       │
│ Done — one staged patch, nothing else in the changeset.                         │
│ …                                                                               │
│ done · 5 rounds                                                                 │
╰─────────────────────────────────────────────────────────────────────────────────╯
╭ Message ────────────────────────────────────────────────────────────────────────╮
│ › █ Ask about the wiki…                                                         │
╰─────────────────────────────────────────────────────────────────────────────────╯

Press ctrl+r to jump to Review. The Ops panel on the left lists operations with a state glyph. The Diff panel on the right shows each op's rationale and provenance above its hunks:

Lint, Log, Browse

  • Lint: findings listed by severity. enter opens the page in Browse.
  • Log: journal events. f cycles the filter (all → accepted → rejected → agent → human). r reverts the selected commit into a new changeset.
  • Browse: the page tree. / finds a page, h/l collapse or expand a folder, e opens the page in $EDITOR (reindexing and relinting on exit), o opens a cited PDF at the cited page.

Most keys can be rebound in ~/.config/lw/hotkeys.toml. See hotkeys.md.

Reading a conversation back

Every agent conversation is saved under the changeset it opened, and stays after commit or reject:

$ lw session list
ID         STATE      STARTED               RECORDS  BYTES
cs-fd447f  open       2026-09-16T12:00:06Z  10       15379
cs-bfa09e  rejected   2026-09-16T11:55:44Z  10       16158
cs-614c83  committed  2026-09-16T11:51:12Z  17       44643

$ lw session show fd447f --plain     # full tool args + results; --thinking, --json
$ lw trace                           # per-turn traces; lw trace show <ref> to inspect one
Try it
On Ask, type: "Stage one patch only: add a short Trade-offs section to wiki/concepts/kv-cache.md, per the ingested source." Press ctrl+r, then p to preview the page, p again to go back to the diff, and C to commit.

08History & undo

Goal: find out what happened, and roll back with the same review you'd give any change.

$ lw log --limit 20
2026-09-15T20:20:04Z changeset_opened changeset=cs-92c7d850b461792a actor=agent message="ingest ~/Downloads/kv-cache-explained.md"
2026-09-15T20:20:23Z op_proposed changeset=cs-92c7d850b461792a op=op1 actor=agent paths=raw/articles/kv-cache-explained.md
…
2026-09-15T20:25:55Z commit_end changeset=cs-92c7d850b461792a commit=000001 actor=agent message="first pages from kv-cache-explained" data={"lint_errors":0,"lint_warns":0}

Filters: --agent, --rejected, --limit N, --page <path>, --since <date>.

Revert opens a changeset, it doesn't write

$ lw revert 000001
opened cs-c5b709e6ddbd1832: revert of 000001 (skipped: index.md, raw/articles/kv-cache-explained.md)
skipped: index.md
skipped: raw/articles/kv-cache-explained.md
  • raw/ is skipped because it's immutable. A revert undoes the pages a source produced, never the source itself.
  • Reverted pages become retraction stubs, so links and index.md entries that point at them still resolve.

Then lw commit -m "revert 000001", or change your mind with lw doctor --discard-changeset.

Only one changeset is open at a time Ingest, Ask and lint --fix add their ops to the open changeset, and you review and commit them together. lw revert is the exception: it refuses while a changeset is open, so commit or discard that one first.

Quick notes (no LLM, no review)

lw note -m "check whether paged attention changes the KV-cache trade-off"
lw note -F draft.md     # from a file; -F - reads stdin
lw note                 # compose in $VISUAL / $EDITOR
lw note list -n 10
lw note list --pending   # only notes not yet distilled into a raw source

Notes go into notes/, outside the wiki. They're never indexed or snapshotted. Think of it as an inbox for thoughts you'll turn into sources later. An editor that returns at once without waiting (like subl or code without -w) is refused naming export EDITOR="... -w"; whatever you save is preserved in .llmwiki/tmp/NOTE_EDITMSG and the next lw note reopens it.

When you want a note to become wiki pages, ingest it by its id. A unique prefix is enough, and --note can be repeated:

$ lw ingest --prepare --agent claude-code --note 20261101-162911-compare
$ lw ingest --note 20261101-162911-compare      # or with lw's own curator and a provider key

12Ask with your own agent

Goal: answer questions from your vault using your own agent, with no API key in lw, no changeset opened, and full access to staged content.

Just as you can curate ingests with an external agent (lesson 11), you can also answer questions using Claude Code, Codex, or Antigravity. This requires no API key configured in lw and uses no provider quota. If your configured model is unfunded or rate-limited, lw query prints a fallback hint pointing here (see lesson 6).

1 · Prepare the ask

Run lw query --prepare "<question>". It prints an ask brief on stdout and exits immediately:

$ lw query --prepare "What is the KV cache?"
# lw query --prepare — ask brief
question: What is the KV cache?

## How to work

Every call is `lw tool --ask <name> '<json>'`, or `lw tool --ask <name> --from -` with a heredoc. The key names matter. The shape of the tools you will reach for first:

    lw tool --ask wiki.search '{"q":"kv cache","limit":5}'
    lw tool --ask wiki.get '{"page":"wiki/concepts/kv-cache.md"}'
    lw tool --ask raw.get '{"source":"raw/articles/x.md","chunk":1}'
    lw tool --ask raw.list '{"query":"kv"}'

`lw tool --ask --list` prints every tool you may call, with its JSON schema. If you lose this brief, run the same `lw query --prepare` again.

1. Find the relevant pages with `wiki.search` and read them with `wiki.get`; read the cited raw source with `raw.get` when a page is thin. Several calls may run in parallel.
2. Answer the question in your reply, following the answer rules below. End every claim drawn from the vault with its `^[raw/...]` marker.
3. A result marked as staged comes from the open changeset, which no human has reviewed yet. Cite it as usual. When a call prints a line starting `note:` on stderr, end your answer with that line, verbatim.
4. A refusal exits 1 and its text says how to fix the call; fix it and call again.
5. This is read-only. No changeset is opened and `lw tool --ask` offers no staging tool. You have a shell, but never edit vault files and never run `lw commit`.
…

Unlike lw ingest --prepare, no changeset is opened and no file lock is held. Asking is purely read-only, so multiple questions can run in parallel without blocking each other or vault curation.

2 · Read tools via lw tool --ask

The agent calls read-only tools via lw tool --ask <name> '<json>'. Run lw tool --ask --list to see the full list of 8 schemas:

  • wiki.search — search committed pages and unreviewed pages in the open changeset
  • wiki.get — read page content, frontmatter, and citations
  • raw.get — read chunks of raw source documents
  • raw.list — list available raw sources matching a query
  • wiki.backlinks — find pages that link to a given page
  • wiki.neighbors — inspect immediate graph neighbors
  • vault.orient — get vault schema, tags, and structure
  • wiki.lint — check health and integrity
$ lw tool --ask wiki.search '{"q":"kv"}'

Staged content and reminder notes

When an open changeset exists in the vault, wiki.search projects the staged pages and tags them (staged in cs-..., unreviewed). If the agent reads unreviewed content, lw tool --ask prints a reminder note to stderr:

The brief instructs the agent to include this line verbatim at the end of its answer, ensuring you always know when an answer draws from uncommitted work.

No. Asking with an agent is completely read-only. No changeset is opened, no .llmwiki/tmp/tool.lock is held, and other processes can continue working in the vault concurrently.

13One vault on every PC

Goal: synchronize your vault across machines through a bare git repo over SSH, with automated pull and push, and conflict handling.

lw sync keeps the exact same wiki on your laptop, workstation, and remote servers. It synchronizes your vault through a bare Git repository over SSH, transferring wiki pages and changelog commits with standard Git while syncing content-addressed storage files beside it.

1 · Set up a remote

Create a bare Git repository on your server (or locally to test) and initialize sync:

$ git init --bare /tmp/lw-remote.git
Initialized empty Git repository in /tmp/lw-remote.git/
$ lw sync init /tmp/lw-remote.git
To /tmp/lw-remote.git
 * [new branch]      HEAD -> main
pushed 1 commit(s) to /tmp/lw-remote.git
config: [vault] path = /home/you/my-vault
config: [sync] remotes = ["/tmp/lw-remote.git"]

This pushes your vault history to the remote and saves the path in ~/.config/lw/config.toml under [sync] remotes.

2 · Check status and clone

Check synchronization state with lw sync status, or pull changes explicitly with lw sync:

$ lw sync status
remote   /tmp/lw-remote.git
ahead    0
behind   0
format   4 (this lw: 4)
last     2026-10-28T10:02:15Z
$ lw sync

To clone your vault onto a second computer:

$ lw sync clone /tmp/lw-remote.git ~/vault-clone
cloned /tmp/lw-remote.git into /home/you/vault-clone

Automatic pull and push

You rarely need to run lw sync by hand:

  • Writing verbs auto-pull: before running lw ingest, lw commit, lw reject, or lw note, lw automatically pulls remote commits to ensure you build on the latest state.
  • Writing verbs auto-push: after committing a changeset or saving a note, lw pushes the new commit (and any new storage objects) immediately to all configured remotes.
  • Read-only verbs stay local: lw query, lw diff, and lw status never touch the network, keeping browsing fast and usable offline.

Keep every PC on the same lw, and conflicts

Since v2.55.0 the first lw commit in a vault stamps .llmwiki/format, and every lw checks it. A vault written by a newer lw is refused by an older one with an upgrade lw message, before anything is read or written:

$ lw lint
lw: lint: vault format 99 is newer than this lw supports (4): upgrade lw   # exit 1

So after you upgrade lw on one PC, upgrade it on your other PCs before you sync. The current format is 4 (since v2.57.0). An lw older than v2.57.0 does not know format 4, so it refuses such a vault; upgrade it before you sync from it. A vault that was never committed to since v2.55.0 has no stamp yet, so the gate cannot protect it; commit once.

If two machines commit diverging changes, lw attempts a clean fast-forward rebase. If an irreconcilable conflict occurs, lw sync --take-remote accepts the remote version as authoritative and preserves your local branch for reference.

Your phone: notes through Syncthing

The phone runs Syncthing and Obsidian only: no git, no lw, no agent. It never talks to the remote. Syncthing carries notes/ and ledger/ between the phone and one PC, the bridge, and that PC's lw sync takes them the rest of the way:

phone (Obsidian)  --Syncthing-->  bridge PC vault  --lw sync-->  remote  -->  your other PCs
  notes/, ledger/                   lw-notes-sync skill
Why not git on the phone too? A second path to the remote means two writers that can diverge, and the phone has no lw to rebase, refuse a conflict, or import receipts. One bridge keeps a single writer per device: Syncthing for the phone, lw sync for PCs. The price: the bridge PC has to be on for phone notes to reach the remote.

Set it up once.

  1. Install Syncthing-Fork and Obsidian on the phone, Syncthing on the bridge PC, and pair the two devices.
  2. Before sharing the vault folder, create .stignore at the vault root on both sides (Syncthing does not sync this file): 
    !/notes
!/ledger
*
    First match wins: keep notes/ and ledger/, ignore the rest. A skip list (wiki, raw, …) is the wrong shape: it still syncs index.md, log.md, .obsidian/ and anything at the vault root.
  3. Share the vault folder; on the phone, point it at an empty folder and open that folder in Obsidian as a vault.
  4. On the bridge PC, keep Syncthing's .stfolder/ marker out of git. lw sync owns .gitignore, so use the PC's own exclude file: 
    $ echo '/.stfolder/' >> ~/my-vault/.git/info/exclude
    Without it, lw sync commits the marker and pushes it to every PC. (The lw-notes-sync skill adds the line for you the first time.)
  5. In Obsidian, on the phone and on every PC: Settings → Files & links → Default location for new attachments → Same folder as current file.
  6. Install the agent skills on each PC from the lw repo: git pull && sh skills/install.sh.

Every day. Write on the phone; drafts are fine, nothing is compiled. On the bridge PC, tell your agent sync my notes. The lw-notes-sync skill moves a stray pasted image beside the note that embeds it, runs lw ledger check and lw ledger import, then lw sync, and reports. Without an agent, the same is lw ledger check && lw ledger import && lw sync (move stray images yourself). When a note is finished, ingest it from any PC: lw ingest --note <id> or ingest note <id> to your agent.

An image pasted at the phone's vault root never leaves the phone. The .stignore above ignores the vault root, so the note arrives with a dangling ![[Pasted image ….png]], and a later ingest keeps it dangling with no lint warning. The skill reports it as missing:; fix it on the phone by moving the image into the note's folder, then sync again. Step 5 above prevents it.
Try it
On the phone, write a note in notes/ with a pasted image. On the bridge PC say sync my notes, then on a second PC run lw sync and open the note: the image should be beside it.
Check: you ran `lw commit` on your desktop. Do you need to run `lw sync` before shutting down?

No. Writing verbs like lw commit, lw reject, and lw note automatically push to configured sync remotes when they finish.

14Files and originals

Goal: preserve raw source originals, bundle local markdown images, and manage non-wiki binaries with content-addressed storage.

A wiki often lives alongside non-text assets: original source files, figures and diagrams in markdown notes, and large binary artifacts like model weights or datasets. lw provides dedicated mechanisms to preserve originals, bundle images, and store non-wiki files without bloating Git.

Verbatim originals beside raws

Whenever you ingest a source, lw ingest saves a verbatim original copy right beside the compiled markdown in raw/:

  • HTML sources: raw/articles/x.html
  • Plain text: raw/articles/x.txt
  • PDF documents: raw/papers/x.pdf
  • Markdown notes: raw/notes/x.md.orig (suffixed with .orig so wiki linters and readers do not treat them as duplicates)

For raws created before original preservation was introduced, lw ingest --attach <file> backfills the original by matching its SHA-256 body hash against committed raws without needing an LLM call. lw doctor tracks this in its originals check.

$ lw ingest --attach unmatched-notes.md
lw: ingest: attach unmatched-notes.md: no committed raw source matches its extracted body (sha256 8c265a4f5bd3) — run lw ingest unmatched-notes.md to ingest it as a new source

Local markdown images in raw/assets/

When ingesting a local markdown file or folder that references images (e.g. ![diagram](fig1.png) or <img src="assets/chart.png">), lw ingest copies the image into raw/assets/<slug>-<name> and rewrites links to relative paths: ../../raw/assets/<name>.

Because raw sources and wiki pages both sit two directories below vault root (raw/<kind>/ and wiki/<type>/), the relative link ../../raw/assets/... resolves identically in both places, previewing seamlessly in Obsidian, VS Code, and GitHub.

Non-wiki storage (lw storage)

To store binary files, benchmarks, or datasets in the vault without polluting Git history, use lw storage:

$ lw storage add weights.bin -m "baseline model weights"
stored weights.bin (14 B, sha256: 3100795e...)
$ lw storage list
NAME         SIZE  ADDED                NOTE
weights.bin  14 B  2026-10-28 10:02:31  baseline model weights
$ lw storage show weights.bin
Name:    weights.bin
Path:    storage/weights.bin
Size:    14 (14 B)
SHA256:  3100795e42b2eb175e3a53bf0787528bf2c1fef29b867b771abbd580ca4f7341
Status:  present
Added:   2026-10-28T10:02:31Z
Note:    baseline model weights

Stored files are tracked in .llmwiki/storage.json and content-addressed under .llmwiki/storage/. When synchronized via lw sync, files travel in <remote>.storage/objects/ alongside Git commits.

Check: does `lw storage add` commit large binary files into your git history?

No. `lw storage` uses content-addressed storage in .llmwiki/storage/ and is excluded from Git commits. When syncing, objects transfer beside Git into <remote>.storage/objects/.

15Troubleshooting

Goal: recognise the common failures by their symptoms.

SymptomCause → fix
Provider returns 400 / 404 / "not found"llm.base_url isn't an OpenAI-compatible /v1 endpoint, or ends in /chat/completions (which lw appends itself). Set it to the API root: lw config set llm.base_url https://…/v1, then lw config --probe.
env:DEEPSEEK_API_KEY (missing) or 401/402/429 on queryExport the variable, or switch to the keyless agent path: run lw query --prepare "<question>" and have an external agent answer with lw tool --ask.
lw note refuses editor exitThe editor returned at once without waiting. Make it wait (e.g. export EDITOR="subl -w" or code -w). Your draft is safe in .llmwiki/tmp/NOTE_EDITMSG and reopens next time.
lw revert: "a changeset is already open"Revert needs a clean slate. Run lw status → lw diff, then commit, press X, or run lw doctor --discard-changeset. (Ingest, Ask and lint --fix join the open changeset instead.)
Ingest interrupted by provider errorIn-stream errors are decoded and retried with backoff. If it still fails, ops staged before the error are kept, marked [partial: …] in the changeset.
Ingest stops: output limit reachedThe default is 32768. If your config sets it lower, raise it with lw config set llm.max_tokens 32768 (lw doctor warns below 16000). Thinking models use a lot of it.
Agent refuses to write a pageIt won't write a claim it can't cite. Ingest a source first. Pages also need at least two outbound [[wikilinks]].
lw: tool: no open changeset — start with lw ingest --prepare <source>lw tool works only inside a prepared ingest. Run lw ingest --prepare first (lesson 11). For questions, use lw tool --ask (lesson 12).
lw tool exits 1Not a crash: the tool refused the call, and stdout says why (a wrong key such as query instead of q, unread chunks, a missing ## Abstract). Fix the arguments and call again.
vault format N is newer than this lw supports (M): upgrade lwAnother PC with a newer lw wrote this vault. Upgrade lw here (reinstall as in lesson 1, then check lw version and which lw your shell finds first). lw refuses rather than guess.
ambiguous note prefix … / no note matching …--note needs an id or a prefix that matches exactly one file in notes/. Run lw note list, copy more of the id.
cite-superseded warningA page still cites an older raw after you re-ingested an edited source. Re-point it with a reviewed patch (lesson 3), or ignore it if the old wording is what the page should keep.
aliases: or another list key came back empty on a pageA rewrite by lw v2.61.0 or older flattened it. Upgrade lw on every PC, retype the key (or, if the vault is under lw sync, take it from the vault's git history) and commit.
warning: lint regresses after ingestThe changeset is still open. Review it with lw diff, drop the bad hunks, or commit with --force (which is recorded in the journal).
