llmwiki

The agent proposes. You commit.

A terminal workbench for LLM-compiled knowledge vaults. The model reads your sources and drafts the wiki, but it never touches the filesystem — every change lands in a staging buffer you review hunk by hunk, the way you review a commit.

The screen that matters

Review

An agent just read three papers and wants to change eleven things. Nothing has been written. Each operation carries the reason it was proposed and the sources it came from, and you can drop a single hunk without rejecting the rest.

The rule everything else follows

One write path

The agent runs with write access denied across the whole vault. Its only way to change anything is a set of validating, graph-aware tools that append to a buffer. That buffer is the only thing a commit can read from.

Agent

Reads freely, writes nothing
  • vault.orient()
  • wiki.search / get / neighbors
  • wiki.lint()
  • raw.get()
→

Buffer  cs-0193f2a

Proposed, not applied
  • stage.create_page()
  • stage.patch_page()
  • stage.rename_page()
  • stage.retract()
→

You  then vault

The only commit authority
  • hunk-level accept / drop
  • atomic apply + snapshot
  • journal record, reindex
  • revert stages the inverse
×

Blocked, and recorded. Write, Edit, rm, mv, cp anywhere under the vault are refused twice — once by the agent's permission profile, once by the engine. Every denial is written to the journal, so a misbehaving agent costs you review time and nothing else.

Why tools instead of a shell

A wiki is a graph, not a folder

Ordinary file commands are the wrong instrument for a linked knowledge base: they cannot see the edges. Each tool below is transactional, validates against SCHEMA.md before it stages anything, and produces a diff a human can read.

Instead ofThe toolWhat the shell cannot know
mv a.md b.mdstage.rename_page That twelve pages link to a. The tool rewrites all of them and stages each rewrite separately.
cat >> page.mdstage.patch_page Which section you meant. Patches are section-scoped (## Related), so they survive reformatting and diff cleanly.
touch new.mdstage.create_page That the tag isn't in the taxonomy, the frontmatter is short a field, or the page has fewer than two outbound links. Rejected at proposal time.
rm old.mdstage.retract That deletion is unrecoverable. Retraction leaves a tombstone and a reason, and the backlinks get fixed.
grep -rwiki.search + wiki.neighbors That assisted-generation already covers this. Graph lookup is what stops duplicate pages.
cat SCHEMA.md index.md…vault.orient Nothing — but making orientation one call means it can't be half-done. Schema, index and the last 30 log entries, always together.
— asking the modelwiki.lint Eleven checks — orphans, broken links, index drift, sha256 source drift, stale pages, tag sprawl — computed in Go. The model only fixes what the engine reports.
Ingest, end to end

From a URL to a commit

Four stages, and a human gate before the third one ends. lw ingest <url> && lw diff && lw commit is the same pipeline without the TUI, so a nightly job can leave you a changeset to read over coffee.

01

Extract

Docling turns the PDF, EPUB or page into markdown. It lands in raw/ with a source URL and a sha256 of the body — the hash is what makes re-ingest incremental and drift detectable. PDFs arrive in v1.0.

Go extractor
02

Compile

The agent orients, searches for existing coverage, and decides what clears the two-source page threshold. It writes pages, cross-references and provenance markers — into the buffer.

agent loop
03

Review

You read the diff. Keep the two new concept pages, drop the entity page for a company mentioned once, accept eleven of twelve backlink rewrites. Each choice is journalled with a reason.

You — the gate
04

Commit

Atomic apply, snapshot, journal record, reindex, and a line appended to log.md. Lint must not regress. lw revert stages the inverse for review rather than applying it.

Decisions, and what they cost

Each of these closed a question. Two of them reversed an earlier call once the evidence came in.

01

No letta-code — we own the loop

Reversed. Embedded chat discards letta's TUI, its Docker image is no longer a supported surface, archival memory would reintroduce the embedding provider we just designed away, and a tool-dispatch regression sits on our hot path. The loop is ~950 lines; integrating letta was budgeted at two weeks. It stays reachable behind a Go interface, and lw mcp still lets it drive the vault.

02

The vault is the agent's memory

No second store. Standing preferences live in curator-memory.md, which the agent edits through stage.patch_page like any other page — so what it learns arrives as a diff you approve, not as state you can't see.

03

One session per changeset

Opening a changeset opens a session; commit or reject closes it and archives the transcript beside the ops. Tool calls that produced staged operations are never compacted away — they are the audit trail. “Why did it propose this?” stays answerable months later.

04

Word search, not FTS5

An in-memory inverted index with BM25-lite ranking. The premise of the whole pattern is that a well-compiled wiki needs less retrieval machinery than RAG does — so ship the simple thing, measure, and add FTS5 or embeddings only where they demonstrably help.

05

Deferred, not dropped

The knowledge graph, PDF ingestion, FTS5 and semantic search, parallel changesets and the multi-vault hub are specified in .dev-notes/PLAN-v2.md; OCR and scanned documents in .dev-notes/PLAN-v2.1.md. Each records why it was deferred and what it plugs into.
